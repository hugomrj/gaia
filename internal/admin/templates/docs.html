GAIA · API

GAIA es un orquestador conversacional para sistemas empresariales. Convierte mensajes en lenguaje natural a instrucciones estructuradas, normaliza datos, y genera respuestas naturales. Está diseñada para ser consumida por cualquier cliente (bot, ERP, CRM) en cualquier lenguaje.

Base URL (desarrollo): http://localhost:8080
Formato: JSON
Autenticación: por definir (multi-tenant, próximamente)

Filosofía

GAIA piensa, el cliente actúa.

  • ✓ GAIA es stateless: no guarda sesiones.
  • ✓ GAIA no conoce las funciones del cliente.
  • ✓ GAIA no ejecuta código ni toca bases de datos.
  • ✓ El cliente es el agente: orquesta, ejecuta y mantiene el historial.
Implicancia clave: el cliente maneja el historial y el estado entre turnos. GAIA solo recibe lo que necesita para procesar cada request.

Arquitectura

Usuario → Cliente → POST /v1/analyze → Planner (¿qué quiere?) → POST /v1/normalize → Normalizer (opcional) → (cliente ejecuta la función real) → POST /v1/synthesize→ Synthesizer (¿cómo lo digo?) → Usuario

Componentes

Componente Rol
Planner Analiza lenguaje natural. Devuelve intent, function_name, parameters y confidence.
Normalizer Convierte valores crudos ("hoy", "150 mil") a formato estándar (ISO 8601, números).
Synthesizer Redacta la respuesta final al usuario. Tiene 4 modos: conversation, clarify, respond, error.

POST /v1/analyze

Analiza el mensaje del usuario y devuelve la intención, el nombre de la función y los parámetros extraídos. El Planner no normaliza valores: los extrae crudos tal como el usuario los escribió.

Request body

Campo Tipo Obligatorio Descripción
session_id string opcional Identificador de la conversación. Útil para logs. GAIA no lo persiste.
message string requerido Mensaje del usuario en lenguaje natural.
collected_data object | null opcional Datos acumulados de turnos previos: intent, function_name, parameters.
history array opcional Últimos turnos (máx. 3) para dar contexto. Ver Manejo del historial.

Ejemplo de request

POST /v1/analyze
Content-Type: application/json

{
  "session_id": "abc-123",
  "message": "cuanto facture hoy",
  "collected_data": null,
  "history": []
}

Response

Campo Tipo Descripción
intent string Intención general en inglés snake_case. Ej: query_billing.
function_name string Función sugerida en inglés snake_case. Ej: get_daily_billing. Vacío si es conversación.
parameters object Valores crudos extraídos del mensaje. Sin normalizar.
confidence number Nivel de confianza (0.0 a 1.0).
original_input string El mensaje original tal como llegó.

Ejemplo de response

{
  "intent": "query_billing",
  "function_name": "get_daily_billing",
  "parameters": {"date": "hoy"},
  "confidence": 0.95,
  "original_input": "cuanto facture hoy"
}
Atención: function_name puede ser un nombre inventado por el LLM que no exista en tu sistema. Es responsabilidad del cliente verificar contra su catálogo antes de ejecutar.

POST /v1/normalize

Convierte valores crudos a formato estándar. Es opcional: el cliente decide cuándo llamarlo. No usa LLM, es determinístico.

Qué normaliza

Tipo Entrada Salida
Fecha relativa "hoy" "2026-10-14"
Período "este mes" {"from": "2026-10-01", "to": "2026-10-31"}
Número "150 mil" 150000
Moneda "150000 Gs." 150000
Booleano "sí" true
Cédula numérica 1234567 "1234567"

Request body

Campo Tipo Obligatorio Descripción
parameters object requerido Parámetros crudos a normalizar.

Ejemplo de request

POST /v1/normalize
Content-Type: application/json

{
  "parameters": {
    "date": "el lunes",
    "amount": "150 mil",
    "is_active": "sí"
  }
}

Ejemplo de response

{
  "parameters": {
    "date": "2026-10-19",
    "amount": 150000,
    "is_active": true
  },
  "normalized": ["date", "amount", "is_active"],
  "not_normalized": []
}
Los valores que no se pueden normalizar se devuelven tal cual y aparecen en not_normalized.

POST /v1/synthesize

Redacta la respuesta final al usuario. Decide el modo automáticamente según los datos que recibe.

Modos automáticos

Modo Cuándo Ejemplo
conversation intent empieza con "conversation" "¡Hola! ¿En qué te ayudo?"
clarify Hay missing_slots sin raw_data "¿Para qué fecha querés la cita?"
respond Hay raw_data y no es error "Tu cita quedó agendada."
error error_code presente o raw_data parece error "No pude procesar tu solicitud."

Request body

Campo Tipo Obligatorio Descripción
original_message string requerido Mensaje original del usuario.
intent string requerido Intención que devolvió el Planner.
function_name string opcional Función que se ejecutó.
parameters object opcional Parámetros usados.
missing_slots array opcional Datos que faltan. Si tiene items → modo clarify.
raw_data string opcional Datos crudos del ERP tras ejecutar. Si está → modo respond.
error_code string opcional Forzar modo error. Valores: function_not_found, execution_failed, timeout.
history array opcional Últimos turnos para dar contexto.

Response

Campo Tipo Descripción
response string Texto natural para mostrar al usuario.
history_entry object Entrada lista para agregar al historial del cliente (con timestamp).
mode string Modo usado: conversation, clarify, respond, error.

Ejemplos por modo

Modo clarify

// Request
{
  "original_message": "quiero una cita",
  "intent": "create_appointment",
  "function_name": "create_appointment",
  "parameters": {},
  "missing_slots": ["date", "doctor"],
  "history": []
}

// Response
{
  "response": "¿Para qué fecha y con qué doctor querés la cita?",
  "history_entry": {
    "role": "assistant",
    "summary": "pedí date, doctor",
    "timestamp": "2026-10-14T10:30:00-03:00"
  },
  "mode": "clarify"
}

Modo respond

// Request
{
  "original_message": "cuanto facture hoy",
  "intent": "query_billing",
  "function_name": "get_daily_billing",
  "parameters": {"date": "hoy"},
  "raw_data": "150000",
  "history": []
}

// Response
{
  "response": "Hoy has facturado un total de 150.000 Gs.",
  "history_entry": {
    "role": "assistant",
    "summary": "respondí sobre query_billing",
    "timestamp": "2026-10-14T10:30:15-03:00"
  },
  "mode": "respond"
}

Modo error

// Request
{
  "original_message": "quiero una cita",
  "intent": "create_appointment",
  "function_name": "create_appointment",
  "raw_data": "ERROR: timeout conectando al ERP",
  "error_code": "execution_failed",
  "history": []
}

// Response
{
  "response": "No pude completar la operación en este momento. ¿Podés intentar de nuevo en unos minutos?",
  "history_entry": {
    "role": "assistant",
    "summary": "error al procesar create_appointment",
    "timestamp": "2026-10-14T10:30:30-03:00"
  },
  "mode": "error"
}

Flujo completo de un turno

1. Usuario escribe un mensaje 2. Cliente → POST /v1/analyze → {intent, function_name, parameters, confidence} 3. Cliente: a. Combina parameters con collected_data b. Verifica si function_name existe en su catálogo c. Calcula missing_slots comparando contra el contrato d. Si no hay missing → ejecuta la función → obtiene raw_data 4. Cliente → POST /v1/synthesize (opcional: /v1/normalize antes) → {response, history_entry, mode} 5. Cliente: a. Muestra response al usuario b. Agrega history_entry al historial local c. Recorta el historial a 6 entradas (3 turnos) d. Guarda collected_data actualizado

Multi-turno (slot filling)

Turno 1: Usuario: "quiero una cita" Planner: {function_name: "create_appointment", parameters: {}} Cliente: calcula missing = ["date", "doctor"] Synthesizer: "¿Para qué fecha y con qué doctor?" Turno 2: Usuario: "el lunes con el doctor ramirez" Planner: {function_name: "create_appointment", parameters: {"date": "el lunes", "doctor": "ramirez"}} Cliente: missing = [] → ejecuta → raw_data = "OK" Synthesizer: "Tu cita quedó agendada para el lunes con el doctor Ramirez."

Manejo del historial

El cliente es responsable de mantener el historial y enviarlo en cada request. GAIA no lo persiste.

Reglas

  • • Máximo 6 entradas (3 turnos de user + assistant).
  • • Se recorta al final del turno, después del /v1/synthesize.
  • • El content del user es el mensaje textual.
  • • El summary del assistant es un resumen corto (lo genera GAIA).
  • • Siempre incluir timestamp en cada entrada.

Estructura

{
  "history": [
    {
      "role": "user",
      "content": "quiero una cita",
      "timestamp": "2026-10-14T10:00:00Z"
    },
    {
      "role": "assistant",
      "summary": "pedí date, doctor",
      "timestamp": "2026-10-14T10:00:02Z"
    }
  ]
}
Importante: el summary no es lo que ve el usuario. Es un resumen para el LLM. El texto real que ve el usuario está en response del /v1/synthesize.

Códigos de error

Códigos HTTP

Código Significado
200 OK. Todo bien.
400 Request inválido. Falta un campo o tiene tipo incorrecto.
401 No autorizado (multi-tenant, próximamente).
500 Error interno. Revisar logs del servidor.
503 Servicio no disponible (LLM caído, cuota agotada).

Error codes en /v1/synthesize

error_code Cuándo usar
function_not_found El function_name que devolvió el Planner no existe en tu catálogo.
execution_failed La función existe pero falló al ejecutar.
timeout El ERP no respondió a tiempo.
invalid_parameters Los parámetros no cumplen el formato esperado.

HistoryEntry

{
  "role": "user" | "assistant",
  "content": "string (solo para user)",
  "summary": "string (solo para assistant)",
  "timestamp": "RFC3339"
}

CollectedData

{
  "intent": "string",
  "function_name": "string",
  "parameters": {},
  "missing_slots": [],
  "status": "ready_to_execute" | "waiting_for_data"
}

Buenas prácticas

1. Validar siempre contra tu catálogo

El Planner puede inventar function_name que no existen. Siempre verificá contra tu lista antes de ejecutar. Si no existe, mandá error_code: "function_not_found" al Synthesizer.

2. Filtrar valores placeholder

El LLM a veces devuelve valores genéricos como "doctor", "value", "unknown". Descartalos antes de ejecutar y agregalos a missing_slots.

3. Recortar el historial

Máximo 6 entradas. Si no recortás, el prompt al LLM crece sin control y sube el costo por request.

4. Manejar errores del ERP

Si la ejecución falla (timeout, excepción), mandá error_code al Synthesizer. Así GAIA responde con una disculpa amable en vez de dejar al usuario sin respuesta.

5. No normalizar dos veces

Si llamás a /v1/normalize, usá los parámetros normalizados para ejecutar la función Y para el Synthesizer. No normalices por un lado y ejecutes por el otro.

6. Resetear collected_data

Cuando el modo del Synthesizer es respond, error o conversation, el turno está cerrado. Reseteá collected_data a null.

7. Session ID (opcional)

Generá un UUID al iniciar cada conversación y usalo en todos los requests. Sirve para logs y para multi-tenant futuro. GAIA no lo persiste.
