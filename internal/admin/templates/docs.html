GAIA · API

GAIA es un orquestador conversacional para sistemas empresariales. Convierte mensajes en lenguaje natural a instrucciones estructuradas, normaliza datos y genera respuestas naturales. Está diseñada para ser consumida por cualquier cliente (bot, ERP, CRM) en cualquier lenguaje.

Base URL (desarrollo): http://localhost:8080
Base URL (producción): https://gaia.japo.click
Formato: JSON
Idioma del contrato: castellano (function_name y parámetros)

Filosofía

GAIA piensa, el cliente actúa.

  • ✓ GAIA es stateless: no guarda sesiones.
  • ✓ GAIA no conoce las funciones del cliente.
  • ✓ GAIA no ejecuta código ni toca bases de datos.
  • ✓ El cliente es el agente: orquesta, ejecuta y mantiene el historial.
Implicancia clave: el cliente maneja el historial y el estado entre turnos. GAIA solo recibe lo que necesita para procesar cada request.

Arquitectura

Usuario → Cliente → POST /v1/analyze → Planner (¿qué quiere?) → POST /v1/normalize → Normalizer (opcional) → (cliente ejecuta la función real) → POST /v1/synthesize→ Synthesizer (¿cómo lo digo?) → Usuario

Componentes

ComponenteRol
Planner Analiza lenguaje natural. Devuelve intent (frase en castellano), is_conversational, function_name, parameters y confidence.
Normalizer Convierte valores crudos ("hoy", "150 mil", "sí") a formato estándar (ISO 8601, números, booleanos). No usa LLM: es determinístico.
Synthesizer Redacta la respuesta final al usuario. Tiene 4 modos: conversation, clarify, respond, error.

POST /v1/analyze

Analiza el mensaje del usuario y devuelve la intención, el nombre de la función y los parámetros extraídos. El Planner no normaliza valores: los extrae crudos tal como el usuario los escribió.

Request body

CampoTipoObligatorioDescripción
messagestring requerido Mensaje del usuario en lenguaje natural.
session_idstring opcional Identificador de la conversación. Útil para logs. GAIA no lo persiste.
function_namestring opcional Función pendiente del turno anterior (slot filling). Si está seteada, el Planner se enfoca en llenar los data_slots nulos.
data_slotsobject opcional Slots acumulados. Un valor null indica "falta este dato". El Planner intenta llenarlo con el mensaje actual.
historyarray opcional Últimos turnos (máx. 6 entradas) para dar contexto. Ver Manejo del historial.

Ejemplo de request

POST /v1/analyze
Content-Type: application/json

{
  "message": "cuanto facture hoy",
  "session_id": "abc-123",
  "history": []
}

Ejemplo con slot filling

POST /v1/analyze
Content-Type: application/json

{
  "message": "el lunes",
  "function_name": "agendar_reunion",
  "data_slots": {
    "doctor": "ramirez",
    "fecha": null
  },
  "history": [...]
}

Response

CampoTipoDescripción
intentstring Frase completa en castellano que resume qué quiere el usuario. Ej: "El usuario quiere saber cuánto se facturó hoy".
is_conversationalboolean true si es charla casual (saludo, agradecimiento, despedida, info del bot, mi perfil). false si es acción.
function_namestring Función sugerida en castellano snake_case (verbo_sustantivo[_sufijo]). Ej: obtener_facturacion_diaria. String vacío si el usuario solo mencionó un tema sin acción.
parametersobject Valores crudos extraídos del mensaje. Sin normalizar.
confidencenumber Nivel de confianza (0.0 a 1.0).
original_inputstring El mensaje original tal como llegó.

Ejemplo de response

{
  "intent": "El usuario quiere saber cuánto se facturó hoy",
  "is_conversational": false,
  "function_name": "obtener_facturacion_diaria",
  "parameters": {"fecha": "hoy"},
  "confidence": 0.95,
  "original_input": "cuanto facture hoy"
}
Atención: function_name puede ser un nombre inventado por el LLM que no exista en tu catálogo. Es responsabilidad del cliente verificar contra su catálogo antes de ejecutar. Si no existe, devolvé error_code: "function_not_found" al Synthesizer.
Topic sin acción: si el usuario dice solo "facturacion" (sin verbo), el Planner devuelve function_name: "" y parameters: {"tema": "facturacion"} con confidence: 0.5. Ese es el caso "topic".

POST /v1/normalize

Convierte valores crudos a formato estándar. Es opcional: el cliente decide cuándo llamarlo. No usa LLM: es determinístico.

Qué normaliza (real)

TipoEntradaSalida
Fecha relativa "hoy", "ayer", "mañana", "pasado mañana", "anteayer" "2026-11-10" (string ISO)
Día de semana "el lunes", "lunes", "el miércoles" "2026-11-16" (próximo día)
Desplazamiento "hace 3 días", "hace 2 semanas", "hace 1 mes", "hace 5 años" "2026-11-07" (string ISO)
Fecha ISO "2026-11-10" Se devuelve tal cual
Fecha con barras "10/11/2026" o "10/11/26" "2026-11-10"
Día + mes "10 de noviembre" o "10 de noviembre de 2026" "2026-11-10"
Año "2026" {"from": "2026-01-01", "to": "2026-12-31"}
Mes "noviembre" o "noviembre de 2026" {"from": "2026-11-01", "to": "2026-11-30"}
Períodos "este mes", "el mes pasado", "esta semana", "el año pasado", "la semana que viene", etc. {"from": "...", "to": "..."}
Número con multiplicador "150 mil", "1.5M", "2 B", "1.5 mil millones" 150000, 1500000, 2000000000
Número con separadores "1.500", "1,500", "1500,50", "1.500,50", "1,500.50" 1500, 1500, 1500.5, 1500.5, 1500.5
Moneda "150000 Gs.", "$1500", "USD 100", "€50", "₲150000" Número sin el símbolo: 150000, 1500, 100
Booleano "sí", "si", "no", "true", "false", "1", "0", "ok" true / false
Cédula numérica 1234567 "1234567" (string, sin notación científica)
Importante: el Normalizer solo intenta interpretar un valor si el nombre del campo lo sugiere o si el valor parece del tipo. Por ejemplo, un campo con nombre is_active, has_stock, activo, etc. se interpreta como booleano. Campos como amount, monto, cantidad se interpretan como número. Ver Modelos de datos.

Request body

CampoTipoObligatorioDescripción
parametersobject requerido Parámetros crudos a normalizar.

Ejemplo de request

POST /v1/normalize
Content-Type: application/json

{
  "parameters": {
    "fecha": "el lunes",
    "monto": "150 mil",
    "is_active": "sí"
  }
}

Ejemplo de response

{
  "parameters": {
    "fecha": "2026-11-16",
    "monto": 150000,
    "is_active": true
  },
  "normalized": ["fecha", "monto", "is_active"],
  "not_normalized": []
}
Los valores que no se pueden normalizar se devuelven tal cual y aparecen en not_normalized. Los arrays contienen nombres de campos (no los valores).

POST /v1/synthesize

Redacta la respuesta final al usuario. Decide el modo automáticamente según los datos que recibe.

Modos automáticos (lógica real)

ModoCondiciónEjemplo de respuesta
conversation is_conversational: true o (sin raw_data, sin slots nulos, confidence ≥ 0.7) "¡Hola! ¿En qué te ayudo?"
clarify Sin raw_data y (hay data_slots con valor null o confidence < 0.7) "¿Para qué fecha querés la cita?"
respond Hay raw_data y no es error "Hoy facturaste Gs 126.825.000."
error error_code presente "No pude completar la operación..."

Bypasses determinísticos (sin LLM)

Estos casos devuelven respuesta hardcodeada, no llaman al LLM:

  • function_name == "obtener_fuera_alcance" → respuesta fija indicando el alcance.
  • error_code == "function_not_found" → respuesta fija indicando que no se puede asistir.

Request body

CampoTipoObligatorioDescripción
original_messagestring requerido Mensaje original del usuario.
intentstring requerido Intención que devolvió el Planner (frase completa en castellano).
function_namestring opcional Función que se ejecutó (o se intentó ejecutar).
is_conversationalboolean opcional Si es true, fuerza modo conversation.
parametersobject opcional Parámetros usados (idealmente normalizados).
data_slotsobject opcional Slots del turno. Un valor null indica que falta y dispara modo clarify (si no hay raw_data).
raw_datastring opcional Datos crudos del ERP tras ejecutar. Si está → modo respond. Idealmente en formato envelope (ver Envelope).
error_codestring opcional Forzar modo error. Valores: function_not_found, execution_failed, timeout, invalid_parameters.
confidencenumber opcional Confianza del Planner. Si es < 0.7 y no hay raw_data, dispara modo clarify.
historyarray opcional Últimos turnos para dar contexto.

Response

CampoTipoDescripción
responsestring Texto natural para mostrar al usuario.
history_entryobject Entrada lista para agregar al historial del cliente (con timestamp).
modestring Modo usado: conversation, clarify, respond, error.
data_slotsobject Eco de los slots del request (útil para el cliente).
raw_datastring Eco del raw_data del request.

Ejemplo modo respond

// Request
{
  "original_message": "cuanto facture hoy",
  "intent": "El usuario quiere saber cuánto se facturó hoy",
  "function_name": "obtener_facturacion_diaria",
  "parameters": {"fecha": "2026-11-10"},
  "confidence": 0.95,
  "raw_data": "{\"type\":\"currency\",\"label\":\"Facturación de hoy\",\"data\":126825000,\"meta\":{\"unit\":\"Gs\"}}",
  "history": []
}

// Response

    "role": "assistant",
    "summary": "obtener_facturacion_diaria(fecha=2026-11-10)",
    "timestamp": "2026-11-10T14:32:00-03:00"
  },
  "mode": "respond",
  "raw_data": "..."
}

Envelope de raw_data

El campo raw_data acepta cualquier string. Si le pasás un envelope JSON, el Synthesizer extrae la información de forma estructurada y la usa para redactar mejor la respuesta. Si no es envelope, se pasa el raw tal cual al LLM.

Formato del envelope

{
  "type":  "currency" | "number" | "text" | "list" | "...",
  "label": "Facturación de hoy",
  "data":  126825000,
  "meta":  {"unit": "Gs", "extra": "..."}
}
CampoTipoDescripción
typestring Tipo semántico. El Synthesizer lo usa para el prompt.
labelstring Descripción legible. Se incluye en el prompt como "descripción".
dataany El valor. Puede ser número, string, array, objeto.
metaobject Metadata opcional (unidad, formato, etc.).
Recomendación: usar siempre envelope. Mejora la calidad de la respuesta y evita alucinaciones sobre qué representa el número.

Flujo completo de un turno

1. Usuario escribe un mensaje 2. Cliente → POST /v1/analyze → {intent, is_conversational, function_name, parameters, confidence} 3. Cliente: a. Verifica si function_name existe en su catálogo b. Calcula data_slots faltantes (los que el Planner marcó como null) c. Si faltan → llama a /v1/synthesize con data_slots null (modo clarify) d. Si no faltan → ejecuta la función → obtiene raw_data 4. Cliente → (opcional) POST /v1/normalize → limpia parámetros crudos antes de ejecutar la función 5. Cliente → POST /v1/synthesize (con raw_data o error_code) → {response, history_entry, mode} 6. Cliente: a. Muestra response al usuario b. Agrega history_entry al historial local c. Recorta el historial a 6 entradas d. Si mode es respond/error/conversation → limpia data_slots

Multi-turno (slot filling)

Turno 1: Usuario: "quiero una cita" Planner: {function_name: "agendar_reunion", data_slots: {doctor: null, fecha: null}} Synthesizer: "¿Con qué doctor y para qué fecha?" Turno 2 (con slots del turno anterior): Usuario: "el lunes con el doctor ramirez" Planner: {function_name: "agendar_reunion", parameters: {fecha: "el lunes", doctor: "ramirez"}} Cliente: normaliza → ejecuta → obtiene raw_data Synthesizer: "Tu cita quedó agendada para el lunes con el doctor Ramírez."

Manejo del historial

El cliente es responsable de mantener el historial y enviarlo en cada request. GAIA no lo persiste.

Reglas

  • Máximo 6 entradas (3 turnos de user + assistant).
  • Se recorta al final del turno, después del /v1/synthesize.
  • El content del user es el mensaje textual.
  • El summary del assistant es un resumen corto (lo genera GAIA).
  • Siempre incluir timestamp en cada entrada.

Estructura

{
  "history": [
    {
      "role": "user",
      "content": "quiero una cita",
      "timestamp": "2026-11-10T10:00:00Z"
    },
    {
      "role": "assistant",
      "summary": "pedí doctor, fecha en agendar_reunion()",
      "timestamp": "2026-11-10T10:00:02Z"
    }
  ]
}
Importante: el summary no es lo que ve el usuario. Es un resumen para el LLM. El texto real que ve el usuario está en response del /v1/synthesize.

Códigos de error

Códigos HTTP

CódigoSignificado
200OK. Todo bien.
400Request inválido. Falta un campo o tiene tipo incorrecto.
500Error interno (LLM caído, error de parseo). Revisar logs.

Error codes en /v1/synthesize

error_codeCuándo usarComportamiento
function_not_found El function_name que devolvió el Planner no existe en tu catálogo. Respuesta hardcodeada (no llama al LLM).
execution_failed La función existe pero falló al ejecutar. Disculpa genérica generada por el LLM.
timeout El ERP no respondió a tiempo. Disculpa genérica + sugerencia de reintentar.
invalid_parameters Los parámetros no cumplen el formato esperado. Disculpa genérica (default).

HistoryEntry

{

DataSlots

Mapa de parámetros pendientes. Un valor null indica "falta este dato" y dispara modo clarify. Un valor presente indica "ya lo tengo". 

{
  "doctor": "ramirez",
  "fecha": null
}

Campos que disparan normalización

El Normalizer mira el nombre del campo para decidir cómo interpretar el valor:

TipoCampos que lo disparan
Fecha / período date, fecha, period, periodo, from, desde, to, hasta, start, end, inicio, fin
Número amount, monto, cantidad, quantity, count, qty, price, precio, saldo, balance, cost, costo
Moneda total, monto_total, importe, subtotal
Booleano prefijos: is_*, has_*, tiene_*, es_*, esta_*, está_*. exactos: active, enabled, activo, habilitado
Cédula / doc cedula, documento, document, ci, ruc, dni, id_number

Vocabulario de funciones (Planner)

El Planner emite function_name usando un vocabulario cerrado en castellano. Formato: verbo_sustantivo[_sufijo] (máx. 3 partes).

Verbos permitidos

obtener_, listar_, buscar_, verificar_, crear_, actualizar_, eliminar_, calcular_, comparar_, generar_, enviar_, agendar_

Sustantivos permitidos

facturacion, clientes, productos, vendedores, categorias, ciudad, saldos, caja, posicion, cuentas, margen, kpis, proveedores, empleados, departamentos, inventario, stock, ordenes, reuniones, resultados, tareas, temas, analisis, informes, reportes

Claves de parámetros permitidas

fecha, periodo, meses, cliente, ciudad, producto, vendedor, monto, cantidad, proveedor, estado, limite, sucursal, tema

Funciones especiales

NombreCuándo aparece
obtener_saludo, obtener_agradecimiento, obtener_despedida, obtener_info_bot, obtener_mi_perfil Cuando is_conversational: true.
obtener_desconocido Mensaje ambiguo sin contexto claro.
obtener_fuera_alcance Pregunta fuera del dominio del sistema.
"" (string vacío) Topic sin acción: usuario mencionó un sustantivo pero sin pedir nada (ej: "facturacion"). Viene con parameters: {"tema": "..."}.
Nota: el vocabulario es la fuente de verdad del contrato. Si tu sistema usa otros nombres, mapealos: la documentación de tu cliente puede usar get_daily_billing y mapear internamente a obtener_facturacion_diaria.

Buenas prácticas

1. Validar siempre contra tu catálogo

El Planner puede inventar function_name que no existen. Siempre verificá contra tu lista antes de ejecutar. Si no existe, mandá error_code: "function_not_found" al Synthesizer.

2. Usar data_slots para slot filling

Si tu función requiere datos que el usuario no dio en un mensaje, guardá function_name y data_slots con los faltantes en null. En el siguiente turno, mandalos en el request de /v1/analyze — el Planner se enfocará en llenarlos.

3. Usar envelope en raw_data

Envolvé la respuesta de tu función en {"type", "label", "data", "meta"}. Mejora la calidad de la respuesta final y reduce alucinaciones numéricas.

4. Recortar el historial

Máximo 6 entradas. Si no recortás, el prompt al LLM crece sin control y sube el costo por request.

5. Manejar errores del ERP

Si la ejecución falla (timeout, excepción), mandá error_code al Synthesizer. Así GAIA responde con una disculpa amable en vez de dejar al usuario sin respuesta.

6. No normalizar dos veces

Si llamás a /v1/normalize, usá los parámetros normalizados para ejecutar la función Y para el Synthesizer. No normalices por un lado y ejecutes por el otro.

7. Limpiar data_slots al cerrar turno

Cuando el modo del Synthesizer es respond, error o conversation, el turno está cerrado. Reseteá data_slots a null (o vacío) en el próximo request.
