GAIA · API

GAIA es un orquestador conversacional para sistemas empresariales. Convierte mensajes en lenguaje natural a instrucciones estructuradas, normaliza datos y genera respuestas naturales. Está diseñada para ser consumida por cualquier cliente (bot, ERP, CRM) en cualquier lenguaje.

Base URL (desarrollo): http://localhost:8080
Base URL (producción): https://gaia.japo.click
Formato: JSON
Idioma del contrato: castellano (function_name y parámetros)

Filosofía

GAIA piensa, el cliente actúa.

  • ✓ GAIA es stateless: no guarda sesiones.
  • ✓ GAIA no conoce las funciones del cliente.
  • ✓ GAIA no ejecuta código ni toca bases de datos.
  • ✓ El cliente es el agente: orquesta, ejecuta y mantiene el historial.
  • ✓ BYOK (Bring Your Own Key): cada tenant usa sus propias API Keys del LLM.
Implicancia clave: el cliente maneja el historial y el estado entre turnos. GAIA solo recibe lo que necesita para procesar cada request.

Arquitectura

Usuario → Cliente → POST /v1/:tenant/analyze → Planner (¿qué quiere?) → POST /v1/:tenant/normalize → Normalizer (opcional) → (cliente ejecuta la función real) → POST /v1/:tenant/synthesize→ Synthesizer (¿cómo lo digo?) → Usuario

Componentes

ComponenteRol
Planner Analiza lenguaje natural. Devuelve intent (frase en castellano), is_conversational, function_name, parameters y confidence.
Normalizer Convierte valores crudos ("hoy", "150 mil", "sí") a formato estándar (ISO 8601, números, booleanos). No usa LLM: es determinístico.
Synthesizer Redacta la respuesta final al usuario. Tiene 4 modos: conversation, clarify, respond, error.

Autenticación y Enrutamiento (BYOK)

Todas las llamadas a los endpoints /v1/:tenant/... requieren autenticación. El tenant (el cliente) se identifica en el path de la URL, y se valida con el token en el header Authorization.

Headers de Configuración

HeaderObligatorioDescripción
Authorization requerido Token del tenant: Bearer gaia_sk_.... Se genera desde el panel de administración.
X-Provider condicional Nombre del LLM (ej: mistral). Obligatorio solo si el tenant tiene 2 o más proveedores con keys activas. Si tiene uno solo, se asume ese.
X-Model opcional Modelo específico a usar (ej: mistral-large-latest). Si no se envía, se usa el default del proveedor (para Mistral es open-mistral-nemo).
BYOK (Bring Your Own Key): GAIA no usa variables de entorno globales. Las API keys del LLM se cargan desde el panel de administración y se asocian a cada tenant. GAIA las elige al azar entre las activas para balancear la carga y evita límites de cuota.

POST /v1/:tenant/analyze

Analiza el mensaje del usuario y devuelve la intención, el nombre de la función y los parámetros extraídos. El Planner no normaliza valores: los extrae crudos tal como el usuario los escribió.

Headers

Authorization: Bearer gaia_sk_...
X-Provider: mistral (opcional/condicional)
X-Model: mistral-large-latest (opcional)

Request body

CampoTipoObligatorioDescripción
messagestring requerido Mensaje del usuario en lenguaje natural.
session_idstring opcional Identificador de la conversación. Útil para logs. GAIA no lo persiste.
function_namestring opcional Función pendiente del turno anterior (slot filling).
data_slotsobject opcional Slots acumulados. Un valor null indica "falta este dato".
historyarray opcional Últimos turnos (máx. 6 entradas) para dar contexto.

Ejemplo de request

POST /v1/demo/analyze
Authorization: Bearer gaia_sk_108a2...
X-Provider: mistral
Content-Type: application/json

{
  "message": "cuanto facture hoy",
  "session_id": "abc-123",
  "history": []
}

Response

CampoTipoDescripción
intentstring Frase completa en castellano que resume qué quiere el usuario.
is_conversationalboolean true si es charla casual.
function_namestring Función sugerida en castellano snake_case.
parametersobject Valores crudos extraídos del mensaje. Sin normalizar.
confidencenumber Nivel de confianza (0.0 a 1.0).
original_inputstring El mensaje original tal como llegó.

Ejemplo de response

{
  "intent": "El usuario quiere saber cuánto se facturó hoy",
  "is_conversational": false,
  "function_name": "obtener_facturacion_diaria",
  "parameters": {"fecha": "hoy"},
  "confidence": 0.95,
  "original_input": "cuanto facture hoy"
}

POST /v1/:tenant/normalize

Convierte valores crudos a formato estándar. Es opcional. No usa LLM ni requiere API keys, pero sí requiere autenticación del tenant en el path.

Qué normaliza (real)

TipoEntradaSalida
Fecha relativa "hoy", "ayer", "mañana" "2026-11-10" (string ISO)
Día de semana "el lunes", "lunes" "2026-11-16" (próximo día)
Número con multiplicador "150 mil", "1.5M", "2 B" 150000, 1500000, 2000000000
Booleano "sí", "si", "no", "true" true / false

Request body

CampoTipoObligatorioDescripción
parametersobject requerido Parámetros crudos a normalizar.

Ejemplo de request

POST /v1/demo/normalize
Authorization: Bearer gaia_sk_108a2...
Content-Type: application/json

{
  "parameters": {
    "fecha": "el lunes",
    "monto": "150 mil",
    "is_active": "sí"
  }
}

Ejemplo de response

{
  "parameters": {
    "fecha": "2026-11-16",
    "monto": 150000,
    "is_active": true
  },
  "normalized": ["fecha", "monto", "is_active"],
  "not_normalized": []
}

POST /v1/:tenant/synthesize

Redacta la respuesta final al usuario. Decide el modo automáticamente según los datos que recibe.

Headers

Authorization: Bearer gaia_sk_...
X-Provider: mistral (opcional/condicional)
X-Model: mistral-large-latest (opcional)

Modos automáticos (lógica real)

ModoCondiciónEjemplo de respuesta
conversation is_conversational: true o (sin raw_data, sin slots nulos, confidence ≥ 0.7) "¡Hola! ¿En qué te ayudo?"
clarify Sin raw_data y (hay data_slots con valor null o confidence < 0.7) "¿Para qué fecha querés la cita?"
respond Hay raw_data y no es error "Hoy facturaste Gs 126.825.000."
error error_code presente "No pude completar la operación..."

Request body

CampoTipoObligatorioDescripción
original_messagestring requerido Mensaje original del usuario.
intentstring requerido Intención que devolvió el Planner.
function_namestring opcional Función que se ejecutó (o se intentó ejecutar).
is_conversationalboolean opcional Si es true, fuerza modo conversation.
parametersobject opcional Parámetros usados (idealmente normalizados).
data_slotsobject opcional Slots del turno. Un valor null dispara modo clarify.
raw_datastring opcional Datos crudos del ERP. Si está → modo respond.
error_codestring opcional Forzar modo error (function_not_found, timeout, etc).
confidencenumber opcional Confianza del Planner. < 0.7 dispara clarify.

Response

CampoTipoDescripción
responsestring Texto natural para mostrar al usuario.
history_entryobject Entrada lista para agregar al historial del cliente.
modestring conversation, clarify, respond o error.

Envelope de raw_data

El campo raw_data acepta cualquier string. Si le pasás un envelope JSON, el Synthesizer extrae la información de forma estructurada y la usa para redactar mejor la respuesta. 

{
  "type":  "currency",
  "label": "Facturación de hoy",
  "data":  126825000,
  "meta":  {"unit": "Gs"}
}

Flujo completo de un turno

1. Usuario escribe un mensaje 2. Cliente → POST /v1/:tenant/analyze → {intent, is_conversational, function_name, parameters, confidence} 3. Cliente: a. Verifica si function_name existe en su catálogo b. Si faltan datos → POST /v1/:tenant/synthesize (modo clarify) c. Si no faltan → ejecuta la función real → obtiene raw_data 4. Cliente → (opcional) POST /v1/:tenant/normalize 5. Cliente → POST /v1/:tenant/synthesize (con raw_data o error_code) → {response, history_entry, mode}

Manejo del historial

El cliente es responsable de mantener el historial y enviarlo en cada request. Máximo 6 entradas. 

{
  "history": [
    {"role": "user", "content": "quiero una cita", "timestamp": "2026-11-10T10:00:00Z"},
    {"role": "assistant", "summary": "pedí doctor, fecha", "timestamp": "2026-11-10T10:00:02Z"}
  ]
}

Códigos de error

Códigos HTTP

CódigoSignificado
200OK.
400Request inválido o error de configuración del tenant (ej: falta key).
401Token inválido o no enviado en el header Authorization.
429Rate limit alcanzado en Mistral (u otro proveedor).
502Error de autenticación con el proveedor LLM (API key revocada).
503Error de conexión con el proveedor LLM.

Errores de configuración (HTTP 400)

MensajeCausa
el tenant no tiene ningún proveedor con API key activa configurada No hay keys cargadas en el panel de administración.
el tenant tiene múltiples proveedores activos; especificá el header X-Provider Tenés 2+ providers vinculados con keys y no enviaste el header.
el proveedor "X" está vinculado al tenant pero no tiene API key activa Pediste un `X-Provider` que existe, pero todas sus keys están apagadas.
el tenant no tiene el proveedor "X" configurado Mandaste un `X-Provider` que ni siquiera está vinculado a tu tenant.

Buenas prácticas

1. Manejar headers dinámicos

Si tu sistema permite a los usuarios cambiar de modelo, solo agregá el header X-Model. Si no, dejá que GAIA use el default (open-mistral-nemo) que es el más económico.

2. Validar contra el catálogo

El Planner puede inventar un function_name. Validalo y respondé con error_code: "function_not_found" al Synthesizer.

3. Usar envelope en raw_data

Envolvé la respuesta de tu función en {"type", "label", "data", "meta"} para evitar que el LLM alucine números.
